# 10 实施计划

状态：设计基线  
当前进度：MVP 已进入实现；实际完成度与已知差距见 [实现状态](13-implementation-status.md)  
原则：先契约和只读，再控制和诊断，最后跨平台发布

## 1. 阶段总览

| 阶段 | 目标 | 核心交付 | 能否使用真实写操作 |
|---|---|---|---|
| 设计基线 | 固定需求、交互、契约和验收 | 本套文档 | 否 |
| P0 | 工程骨架与匿名原型 | Crate、终端、App、Backend、fixtures | 仅模拟 |
| P1 | 真实只读仪表盘 | 七页真实数据、刷新和错误处理 | 否 |
| P2 | 安全控制能力 | 服务、账号、登录和任务状态机 | 是，显式确认 |
| P3 | 诊断与体验完善 | 健康、日志增强、签到、主题和帮助 | 显式消耗/签到 |
| P4 | 双平台测试与发布 | CI、人工矩阵、打包和发布文档 | 发布版本 |
| P5 | 用量分析与视觉升级 | OpenCode 统计、KPI、活动图、模型聚合 | 只读 |

每个阶段必须完成验收后再扩大下一阶段范围。P2 不需要等待所有视觉效果完美，但终端恢复、命令白名单和写任务互斥不能延期。

## 3. P0：工程骨架与匿名原型

### 任务

1. 创建独立 Cargo binary，名称 `router-tui`。
2. 锁定 Ratatui/Crossterm 匹配版本和 Rust MSRV。
3. 实现 CLI 参数骨架：`--router-root`、`--node`、`--demo`、`--read-only`、`--ascii`、主题和刷新参数。
4. 实现终端初始化、幂等恢复、panic hook 和非 TTY 检查。
5. 建立领域模型、App reducer、页面导航和焦点。
6. 建立 Backend 能力接口和 FixtureBackend。
7. 用匿名 fixtures 完成七页基本渲染、弹窗和帮助。
8. 建立基础单元测试与 TestBackend 测试。

### 依赖

- 文档 02、03、04、07、09。
- 不依赖真实 Node 或账号。

### 验收

- Windows/Linux 能编译和运行 demo。
- 无 Node、无 router root 时 demo 仍完整可用。
- 所有页面可键盘导航，80×24 可读。
- 正常退出、panic 和渲染错误能恢复终端。
- demo 不 spawn 任何 Node 进程。

### 不做

- 真实 CLI 控制；
- 真实数据持久化；
- 请求遥测数据库；
- 复杂插件系统。

## 4. P1：真实只读仪表盘

### 任务

1. 实现 root/Node 发现和诊断。
2. 接入 `list --json` 与 legacy/v1 解析。
3. 接入 `account --json`。
4. 接入 `qoder2pi credits json`。
5. 接入 `logs` 和 `doctor` 文本显示。
6. 为 health 增加结构化 JSON；为 auth 增加结构化 state/expiresAt。
7. 实现 Tokio 任务通道、请求 ID、generation、超时和资源状态。
8. 实现状态/额度/日志的差异刷新策略和 stale。
9. 完成局部失败、空状态、全局后端失败和只读模式。
10. 完成假 Node 集成测试。

### 对现有项目的最小增量

- JSON 增量字段和 health JSON 是允许的后端改动。
- 保持原有人类 CLI 输出与写命令语义。
- 不重写 provider 进程控制，不调整账号文件格式。
- 根 README 只增加真实可用入口，不夸大跨平台后端能力。

### 验收

- 启动和自动刷新不执行写命令、不登录、不签到、不真实试打。
- 八家真实只读数据可显示，单家失败不影响其他来源。
- 慢查询不阻塞键盘，旧响应不覆盖新状态。
- models null、空账号、额度失败、Node 缺失均有正确界面。
- 假 Node 契约测试在 Windows/Linux 通过。

## 5. P2：安全控制能力

### 任务

1. 实现 Action 枚举、命令映射和统一调度。
2. 实现普通/高风险确认框和 `--read-only` 后端阻断。
3. 实现写任务全局串行、重复去重和有界任务输出。
4. 接入 up/down/keep-oc/restart/on/off/all/none/sync。
5. 后台启动类命令统一 `--no-login`。
6. 实现操作后状态失效和重新查询。
7. 接入账号 dry-run、正式切换和恢复整池。
8. 实现登录/添加账号的终端挂起与恢复。
9. 完成任务失败、成功未确认和活动任务退出保护。
10. 穷举 Action 命令映射和状态机测试。

### 验收

- 连按和 key repeat 不会重复执行写操作。
- `on` 明确显示其他将被关闭的 provider。
- 普通停止与 keep-oc 的客户端影响文案准确。
- dry-run 不写状态，正式切换后才刷新账号/服务/额度。
- 登录取消和成功都恢复终端。
- 写操作没有普通查询短超时和自动重试。
- 所有真实人工写测试能恢复测试前状态。

### 验收

- 普通刷新和自动任务不触发签到/试打。
- 60 列降级、超小终端、中文宽字符和无色模式可用。
- 日志/任务缓冲有界，长时间运行不无限增长。

## 10. 依赖关系

```text
领域模型 / Backend 接口
       ├── FixtureBackend → UI 原型与渲染测试
       └── NodeBackend    → 真实只读数据
                                  ↓
Action 状态机 → 写命令 → 操作后刷新 → 账号/登录
                                  ↓
                        诊断、签到与真实试打
                                  ↓
                         双平台发布与运维
```

认证结构化字段和 health JSON 是 P1 的后端依赖；若暂缓，TUI 只能显示旧 label/文本，不能自行正则推断高级状态。

## 11. 变更控制

以下变化必须先更新文档再改实现：

- MVP 页面或 provider 范围；
- 写命令及其副作用；
- JSON 必需字段、字段改义或 schemaVersion；
- 默认刷新导致的新网络/额度消耗；
- 新增凭证读取、日志持久化或网络上传；
- 新的操作系统/架构支持承诺；
- 跳过终端恢复、危险确认或写任务互斥。

需求变更应记录原因、影响文档、测试迁移和发布兼容性。不得用“实现更方便”为由悄悄改变 `on/down` 等既有语义。

## 12. 实施完成定义

整个项目 MVP 完成需要：

- P0–P4 验收全部有记录；
- 需求追踪无未解释缺口；
- 安全与跨平台清单全部通过；
- 真实 CLI 人类输出保持可用；
- 文档没有“计划命令”和“现有命令”混用；
- 根 README、tui README、发布说明和实际二进制一致；
- 用户可以在没有 TUI 的情况下继续使用原 CLI，TUI 故障不破坏原配置。
